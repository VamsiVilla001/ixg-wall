          Wall behaviour

          User links

          Whoever opens a user link signs in as a user, with no password. Users operate the wall: order, remove and rename feeds, switch sessions, change the layout and playback. Only admins add feeds or change a feed's link. A link works until you revoke it; revoking it signs out everyone who used it.

          What a link ships is decided here, when you make it. With YouTube on, the wall's viewer counts, likes, broadcast state and ingest health reach the user, read with your API key and channel sign-ins; the user never sees the key, the OAuth client or the sign-ins, and has no YouTube settings at all. With it off, the user gets the players and the measured playback only.

          This wall has no password, so anyone who opens it is already an admin and there's nothing for a link to grant. User links work on a wall with a password: the website, or npm run dev:hosted on this computer.

            Layout

            Every tile keeps one size, so feeds and stats stay legible. The page grows with the feed rows; scroll down for more. The header and playback controls stay visible.

            Pick a layout from the bar under the wall: the six quick ones, or … for the rest and the custom layout builder. It applies to every feed, a screen at a time (2 × 2 with 10 feeds is three pages; the last is only as tall as its feeds). Each page's first feed takes its biggest box: press Main on a feed to put it there, or drag any feed by its picture or name bar to a new place.

            Every feed stays on screen, so tiles shrink as you add feeds.

            With the Feed Meter extension, every feed streams at this quality whatever its size on screen, and changes apply within about 15 s without a refresh; a stream that doesn't offer it plays at the nearest level below. If the link or the computer can't keep up, feeds are held at 480p, priority feeds last. Without the extension, YouTube sizes quality to the player, so only feeds on screen in the scroll and preset layouts get it (one scrolled away drops to 480p after a minute), and lowering it refreshes them.

            YouTube API

            Adds live viewers, likes, views and comments to every feed, and a viewer history with peak, average, lowest and trend: open a feed's Stats for the full analytics. Also privacy, embedding, HD/SD and live chat, at no extra quota. The backend polls YouTube once per interval for every open window: every 30 s uses about 3,000 of the daily 10,000 quota units for up to 50 feeds.

            Any Google Cloud project's key works, whoever it belongs to. Get a key: in Google Cloud, enable YouTube Data API v3, then create an API key under Credentials and restrict it to the YouTube Data API. A new key is checked with YouTube before it replaces the saved one. It stays on the server (secrets.json in its data folder) and is never sent back to a browser. For an address restriction, allow the server's public IP on a hosted wall, or http://localhost:8080/* on the laptop.

            Channel sign-in · ingest health

              Sign in with the Google account of each channel the feeds stream to (read-only). Several channels can be signed in at once: each feed's ingest comes from the channel that owns it. The wall then shows how each feed's encoder stream arrives at YouTube: health (good, ok, bad), resolution, frame rate and YouTube's warnings, refreshed with the numbers above.

              One-time setup, in anyone's Google Cloud project: under Credentials, create an OAuth client ID of type Web application, add this authorised redirect URI, then paste its ID and secret here. The client is checked with Google before it's saved.

              Laptop & rendering

              Measured

              Applies to the managed wall window and restarts it. On the benchmark laptop (Ryzen 5 4600H, Radeon graphics) software decoding dropped 0% of frames at 30 feeds; the GPU decoder dropped 4–7% at 24.

              A website can't choose how the browser decodes video. On a low-spec laptop that drops frames, open the wall from a Chrome shortcut that adds --disable-accelerated-video-decode (software decoding: 0% dropped frames at 30 feeds on the benchmark laptop, against 4–7% on its GPU). DEPLOY.md has the exact shortcut.

              Sync

              Every feed carries the same input, so the wall holds all live feeds at one shared delay, read from YouTube's timestamp on each frame. The delay is the slowest feed's edge delay plus this margin. Feeds that are ahead are held back with YouTube's live rewind; feeds that fall behind catch up. Offsets up to 10 s close smoothly at 0.75× or 1.25×; bigger ones jump (YouTube lands jumps on segment boundaries, so speed finishes the job). A feed whose edge delay is more than 15 s past the others isn't synced, so it can't hold up the whole wall.

              Releasing build-up on this PC

              For feeds outside the sync group. Behind edge is measured from the least delay that feed has reached since it loaded. Up to 15 s closes at 1.25×; more jumps. Three jumps inside two minutes escalate to a full refresh, and anything over 90 s behind jumps regardless.

              Off (0) by default: a feed that plays is left alone, and the wall refreshes a player only when it is stuck or has failed. Set a time to destroy and recreate every player on a schedule, which clears a degraded player and its buffer. It doesn't give memory back on its own: the new player loads into the same browser process (see Memory offload). Refreshes are staggered so the wall never blanks at once.

              Memory offload

              The players of each YouTube site (youtube.com and youtube-nocookie.com) share one browser process, which keeps growing for as long as it runs: this is the "High memory usage" Chrome reports on the wall tab. Refreshing a player doesn't shrink it; only ending the process does. An offload moves the feeds one at a time to the other site, lets Chrome end the emptied process, then does the same the other way. Every feed restarts twice, each like a normal refresh, never more than one at a time, and both processes start fresh.

              In the managed wall window, the backend measures the tab (the page and its players) from Windows, as Chrome's Task Manager counts it. If an offload can't get it under the limit, the feeds need that much: the event log says so, and the wall waits 30 min before trying again. 0 turns this off.

              A web page can't read its own tab's memory, so in an ordinary browser tab, or on a hosted wall, the wall offloads on this timer instead. 0 turns this off.

              Source screenshots

              Takes the same screenshot as Capture source screenshot (Stats sheet), without a click: when a feed's watching-now count reaches a new high (at most once per feed in the time above; the counts are checked at every YouTube refresh), and once when YouTube says a feed's broadcast is over. Files are named with _PEAK_ or _END_ (Feed Meter 1.5) and saved to Downloads/IXG-Wall/Screenshots on the computer that took them. The backend decides when, so with several wall windows open only one takes each screenshot: an admin's window with the Feed Meter. Needs a YouTube API key for the counts. Everything queued, saved, dropped or failed is recorded in the event log under Wall stats.

              What the numbers mean

              A frame travels: encoder → YouTube → network → this PC's player → screen. Each reading belongs to one of those steps.

              Encoder Your side
              Encodes the picture and sends it to YouTube in order. Its own buffer and dropped frames show in the encoder's telemetry. The wall shows how its stream arrives: Ingest health (channel sign-in).
              Edge delay YouTube
              The least delay a feed can have: YouTube receiving, processing and packaging the video, mostly set by the broadcast's latency mode (Normal / Low / Ultra-low in YouTube Studio). The wall can't release it, only report it.
              Connection Network
              How fast YouTube's video reaches this PC against the feed's bitrate. Below 1.2× the bitrate, rebuffering is coming (Feed Meter extension).
              Buffer ahead This PC
              Video already downloaded and waiting to play. A cushion, not delay: red below 4 s.
              Rebuffering This PC
              The player ran out of buffer and stopped. Every second stopped adds to Behind edge.
              Behind edge This PC
              How far the player sits behind the newest video YouTube has. This is the build-up the wall releases: catching up, jumping or refreshing.
              Delay Whole chain
              From YouTube's timestamp on a frame to this screen: Edge delay + Behind edge. It uses this PC's clock, so keep Windows time synced; any clock offset is the same for every feed and doesn't affect sync.
              Sync Wall
              Each feed's offset from the wall's shared delay. + has more delay than the others, − less. Green within ±0.3 s.

              Bandwidth & loading

              Your link's download speed from a speed test. Priority feeds are only boosted while the wall's estimated load stays under 80% of it. 0 means unknown: boosts are granted and shed one at a time when several feeds stall together.

              Feeds load in order, priority first, so startup and refreshes never hit the link all at once.
